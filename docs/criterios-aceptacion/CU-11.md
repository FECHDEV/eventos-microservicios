# CU-11 — Gestionar tipos de entradas — Criterios de aceptación

## Contexto

El Administrador consulta los tipos de entrada de un evento, con su precio y su
disponibilidad, registra tipos nuevos y modifica los existentes: nombre, precio
y cantidad total. Cubre RF-13 y RF-14.

Fuentes: ficha CU-11 (`docs/casos-de-uso.md`); `docs/decisiones.md` → Gestión de
Eventos ("Estado `BORRADOR`", "Edición de un evento según su estado", "Tipos de
entrada según el estado del evento", "Cambiar la cantidad total de un tipo",
"Precio de un tipo de entrada", "Nombre único dentro del evento" y "Los tipos de
entrada no se eliminan") y Venta ("`cantidad_disponible` se descuenta al
reservar", "Concurrencia sobre el último cupo" y "Precio congelado en
`reserva.precio_unitario`"); clase `TipoEntrada` y tabla `tipo_entrada`
(`docs/modelo-diseno-y-datos.md` 1.1 y 2.3); `CLAUDE.md` → Entradas y Usuarios y
roles.

Las cinco decisiones de estado, cantidad, precio, nombre y eliminación se tomaron
con el usuario al generar estos criterios. Ninguna amplía el modelo de Fase 4.

## Requisitos funcionales (EARS)

**Acceso** *(precondición 1; actor principal)*
- RF-1: SI la petición no tiene una sesión válida, ENTONCES EL SISTEMA rechaza la
  consulta y los cambios como no autenticados (401 `NO_AUTENTICADO`). *(CU-02)*
- RF-2: SI el Usuario de la sesión no tiene rol ADMINISTRADOR, ENTONCES EL
  SISTEMA rechaza la consulta y los cambios (403 `ACCESO_DENEGADO`).
  *(`CLAUDE.md`: el control de acceso se valida en el backend)*

**Consultar** *(ficha, pasos 1-2)*
- RF-3: CUANDO el Administrador pide los tipos de entrada de un evento, EL
  SISTEMA muestra todos los de ese evento, en el orden en que se registraron, con
  nombre, precio, cantidad total y cantidad disponible. *(paso 2; RF-14 de
  Análisis: "consulta la disponibilidad existente")*
- RF-4: CUANDO el evento no tiene tipos de entrada, EL SISTEMA devuelve una lista
  vacía, no un error. *(un evento en BORRADOR recién registrado)*
- RF-5: EL SISTEMA permite consultar los tipos en cualquier estado del evento,
  incluido CANCELADO. *(decisiones.md → Tipos de entrada según el estado)*
- RF-6: SI el evento no existe, ENTONCES EL SISTEMA responde 404
  `EVENTO_NO_ENCONTRADO`, tanto al consultar como al registrar o modificar.

**Registrar** *(ficha, pasos 3-6; postcondición 1)*
- RF-7: CUANDO el Administrador registra un tipo de entrada con datos válidos, EL
  SISTEMA lo asocia al evento con la cantidad disponible igual a la total, y
  confirma devolviendo el tipo registrado.
- RF-8: SI falta el nombre, el precio o la cantidad total, ENTONCES EL SISTEMA no
  registra el tipo e indica los campos a corregir (400 `DATOS_INVALIDOS`, con el
  mismo formato que CU-01). *(FA-01; columnas NOT NULL de `tipo_entrada`)*
- RF-9: SI el nombre supera 80 caracteres, ENTONCES EL SISTEMA no registra el
  tipo e indica el campo a corregir. *(tabla `tipo_entrada`)*
- RF-10: SI el precio no es mayor que 0, tiene más de 2 decimales o supera
  99.999.999,99, ENTONCES EL SISTEMA no registra el tipo e indica el campo a
  corregir. *(FA-01; decisiones.md → Precio de un tipo de entrada)*
- RF-11: SI la cantidad total es menor que 1, ENTONCES EL SISTEMA no registra el
  tipo e indica el campo a corregir. *(FA-01; decisiones.md → Cambiar la
  cantidad total)*
- RF-12: SI el evento ya tiene otro tipo con el mismo nombre, sin distinguir
  mayúsculas ni espacios en los extremos, ENTONCES EL SISTEMA no registra el tipo
  y responde 409 `TIPO_ENTRADA_DUPLICADO`. *(decisiones.md → Nombre único
  dentro del evento)*

**Modificar** *(ficha, pasos 3-6)*
- RF-13: CUANDO el Administrador modifica un tipo con datos válidos, EL SISTEMA
  registra el nombre, el precio y la cantidad total nuevos y confirma devolviendo
  el tipo actualizado, con las mismas reglas de RF-8 a RF-12. Un tipo no choca
  con su propio nombre.
- RF-14: CUANDO cambia la cantidad total, EL SISTEMA mueve la cantidad disponible
  en la misma diferencia. *(decisiones.md → Cambiar la cantidad total)*
- RF-15: SI la nueva cantidad total es menor que lo ya vendido y reservado
  (`cantidad_total - cantidad_disponible`), ENTONCES EL SISTEMA no registra
  ningún cambio e indica el campo a corregir con el mínimo posible (400
  `DATOS_INVALIDOS`). *(FA-01; decisiones.md → Cambiar la cantidad total)*
- RF-16: CUANDO cambia el precio, EL SISTEMA lo aplica a las reservas siguientes
  sin tocar las existentes. *(decisiones.md → Precio congelado; el precio vive en
  `reserva.precio_unitario`, que CU-06 copia al reservar)*
- RF-17: SI el tipo no existe o pertenece a otro evento, ENTONCES EL SISTEMA
  responde 404 `TIPO_ENTRADA_NO_ENCONTRADO`.
- RF-18: SI la modificación trae la cantidad disponible, ENTONCES EL SISTEMA la
  ignora: solo se deriva de la total. *(decisiones.md → Cambiar la cantidad
  total)*

**Según el estado del evento** *(decisiones.md → Tipos de entrada según el estado)*
- RF-19: MIENTRAS el evento está en BORRADOR, ACTIVO o POSTERGADO, EL SISTEMA
  permite registrar y modificar sus tipos.
- RF-20: SI el evento está CANCELADO, ENTONCES EL SISTEMA no registra ni modifica
  ningún tipo y responde 409 `EVENTO_CANCELADO`.

**Concurrencia** *(decisiones.md → Concurrencia sobre el último cupo)*
- RF-21: EL SISTEMA modifica un tipo con su fila bloqueada, para que un cambio
  de cantidad y una reserva simultánea (CU-06) no pisen la cantidad disponible.
- RF-22: EL SISTEMA registra y modifica los tipos con el evento bloqueado, para
  que dos pedidos simultáneos no creen dos tipos con el mismo nombre ni cambien
  un tipo de un evento que se está cancelando.

## Casos límite

- **Nombre de solo espacios:** cuenta como vacío (RF-8). Se guarda sin los
  espacios de los extremos.
- **"VIP" y " vip ":** chocan en el mismo evento (RF-12); en eventos distintos,
  no.
- **Renombrar "VIP" a "vip":** no choca consigo mismo (RF-13).
- **Precio 0, negativo o 10,999:** se rechazan (RF-10). **10,5:** se acepta y se
  guarda como 10,50.
- **Precio como texto o con formato inválido en el JSON:** 400
  `DATOS_INVALIDOS`.
- **Cantidad total igual a lo vendido y reservado:** se acepta y la disponible
  queda en 0 (RF-15).
- **Cantidad total que no entra en un entero:** 400 `DATOS_INVALIDOS`.
- **Tipo de otro evento en la URL:** 404 `TIPO_ENTRADA_NO_ENCONTRADO`, no se
  modifica (RF-17).
- **Evento ACTIVO con ventas:** se le agrega un tipo nuevo y se sube el cupo de
  uno existente (RF-19).
- **Evento en BORRADOR con la fecha en el pasado:** sus tipos se siguen
  editando; la fecha es asunto de CU-10.
- **Mientras no exista CU-06:** nadie reserva, así que la disponible es igual a
  la total. RF-15 y RF-21 se prueban poniendo la disponible en la base.

## Fuera de alcance

- Eliminar tipos de entrada (decisiones.md → Los tipos de entrada no se
  eliminan).
- Entradas gratis: el precio es siempre mayor que 0 (decisiones.md → Precio de un
  tipo de entrada).
- Activar el evento y verificar que tenga al menos un tipo: CU-12.
- Reservar, descontar y liberar disponibilidad: CU-06.
- Mostrar los tipos al cliente: CU-05.
- Selección de asientos (`CLAUDE.md` → Entradas).
- Pantallas: se entregan aparte, en el frontend de administración de eventos,
  que junta CU-10, CU-11 y CU-12 (`docs/plan-implementacion.md` → Excepción en
  Gestión de Eventos; plan en `docs/superpowers/plans/2026-09-21-frontend-admin-eventos.md`).

## Criterios de finalización

- Cada RF con test en verde en `./mvnw test`: entidad, repositorio, servicio,
  endpoints e integración de extremo a extremo. Los tests de CU-01 a CU-10 siguen
  en verde.
- Prueba manual contra MySQL con el Administrador inicial y `ana@mail.com`:
  - **Acceso:** sin token → 401; con el token de ana (CLIENTE) → 403.
  - **Consultar:** un evento sin tipos → lista vacía; uno inexistente → 404.
  - **Registrar:** "General" a 50 Bs con 100 → disponible 100. Precio 0,
    cantidad 0 o nombre vacío → 400 con los campos. " general " en el mismo
    evento → 409.
  - **Modificar:** subir el precio y la cantidad; con la disponible puesta en la
    base por debajo de la total, bajar la total por debajo de lo vendido → 400
    con el mínimo, y justo en el mínimo → disponible 0.
  - **Estado:** un evento CANCELADO (puesto así en la base mientras no exista
    CU-12) → 409 al registrar y al modificar; su lista sigue visible.
- `/code-review` sin hallazgos pendientes. `/security-review` no corresponde: no
  abre superficie nueva de datos externos.
- El backend se cierra con este CU. Sus pantallas se prueban en el navegador y
  se revisan con el frontend de administración de eventos (`docs/superpowers/plans/2026-09-21-frontend-admin-eventos.md`).
