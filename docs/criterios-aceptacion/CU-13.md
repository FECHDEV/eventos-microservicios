# CU-13 — Gestionar devoluciones — Criterios de aceptación

## Contexto

El Administrador identifica las entradas de los eventos cancelados y registra
que se devolvieron, una vez hecha la devolución económica fuera del sistema.
Cubre RF-39, RF-40, RF-41 y la parte de RF-34 que le toca. Cierra el subsistema
de Pagos.

**Fuentes:**
- Ficha CU-13 (`docs/casos-de-uso.md`).
- `docs/decisiones.md`:
  - «CU-13 devuelve solo entradas activas».
  - «Pago tardío»: ningún CU registra la devolución de un pago tardío.
  - «Ingresos: bruto, devuelto y neto»: el pago de una entrada devuelta sigue
    figurando como pagado.
  - «CU-05 lista eventos activos y postergados»: un evento cancelado es el
    camino a la devolución.
- Clase `Entrada` (operación `marcarDevuelta()`) y tabla `entrada`
  (`docs/modelo-diseno-y-datos.md` 1.1 y 2.6).
- `docs/requisitos-no-funcionales.md`: RNF-01 a RNF-03 y RNF-14.
- `CLAUDE.md`: Entradas, Cancelación y Correos.

Tres decisiones se tomaron con el usuario al generar estos criterios
(`decisiones.md` → «Gestionar devoluciones (CU-13)»). Ninguna cambia el modelo
de Fase 4.
1. **El registro es el estado DEVUELTA.** No se guarda la fecha ni quién la
   registró: el modelo no lo tiene, y la devolución económica y su comprobante
   viven fuera del sistema.
2. **Por compra.** Las entradas pendientes se agrupan por compra; se registra la
   compra entera (todas sus activas) o una sola entrada.
3. **Las devueltas a la vista.** La pantalla del evento muestra aparte, solo
   lectura, las entradas ya devueltas.

## Requisitos funcionales (EARS)

**Acceso** *(precondición 1; RNF-01)*

- RF-1: SI la petición llega sin sesión o con un token inválido, ENTONCES EL
  SISTEMA la rechaza (401 `NO_AUTENTICADO`). SI el Usuario no tiene rol
  ADMINISTRADOR, ENTONCES la rechaza (403 `ACCESO_DENEGADO`).

**Eventos cancelados** *(pasos 1 y 2; precondición 2)*

- RF-2: CUANDO el Administrador accede a la gestión de devoluciones, EL SISTEMA
  muestra los eventos CANCELADOS, del más reciente al más antiguo, con cuántas
  entradas pendientes de devolución tiene cada uno.
- RF-3: SI no hay eventos cancelados, ENTONCES EL SISTEMA informa que no hay
  devoluciones que gestionar. *(precondición 2)*

**Entradas de un evento** *(pasos 3 a 5; decisiones con el usuario)*

- RF-4: CUANDO el Administrador selecciona un evento cancelado, EL SISTEMA
  muestra sus entradas ACTIVAS, que son las pendientes de devolución, agrupadas
  por compra:
  - el Cliente: nombre, correo y teléfono;
  - el tipo de entrada, la cantidad de la compra y el monto pagado;
  - la fecha de pago;
  - las entradas, numeradas.

  *(paso 4)*
- RF-5: EL SISTEMA muestra aparte, solo lectura, las compras con entradas
  DEVUELTAS del evento. *(postcondición 2: el sistema conserva el registro de la
  devolución)*
- RF-6: EL SISTEMA no muestra las entradas UTILIZADAS: corresponden a alguien
  que ya asistió y no se devuelven. *(decisiones.md → CU-13 devuelve solo
  entradas activas)*
- RF-7: SI el evento no tiene entradas pendientes, ENTONCES EL SISTEMA lo
  informa y permite volver a la lista de eventos. *(FA-01)*
- RF-8: SI el evento no existe, ENTONCES EL SISTEMA responde 404
  `EVENTO_NO_ENCONTRADO`. SI existe pero no está cancelado, ENTONCES responde
  409 `EVENTO_NO_CANCELADO`.

**Registrar la devolución** *(pasos 6 y 7)*

- RF-9: CUANDO el Administrador registra la devolución de una compra, EL SISTEMA
  pasa a DEVUELTA todas sus entradas ACTIVAS y confirma cuántas registró.
- RF-10: CUANDO el Administrador registra la devolución de una sola entrada
  ACTIVA, EL SISTEMA la pasa a DEVUELTA y lo confirma.
  *(`Entrada.marcarDevuelta()`)*
- RF-11: SI la entrada ya está DEVUELTA, o la compra ya no tiene entradas
  activas, ENTONCES EL SISTEMA lo informa y no registra nada (409
  `ENTRADA_YA_DEVUELTA`). *(FA-02)*
- RF-12: EL SISTEMA solo registra entradas ACTIVAS de un evento CANCELADO. SI la
  entrada está UTILIZADA, ENTONCES responde 409 `ENTRADA_NO_DEVOLVIBLE`; SI su
  evento no está cancelado, 409 `EVENTO_NO_CANCELADO`. SI la entrada no existe,
  404 `ENTRADA_NO_ENCONTRADA`; SI la compra no existe o no tiene entradas, 404
  `COMPRA_NO_ENCONTRADA`. En ningún caso la registra. *(códigos fijados al
  planificar)*
- RF-13: SI dos Administradores registran la misma entrada o compra a la vez,
  ENTONCES EL SISTEMA la registra una sola vez y al segundo le responde como en
  FA-02. *(la actualización está condicionada a que la entrada siga ACTIVA)*
- RF-14: EL SISTEMA pide confirmación antes de registrar una devolución: no se
  deshace.

**Lo que no cambia** *(`CLAUDE.md` → Cancelación; decisiones.md → Ingresos)*

- RF-15: EL SISTEMA no modifica el pago, que sigue PAGADO, no envía correos ni
  devuelve dinero: solo registra el estado de la entrada. *(la devolución
  económica ocurre fuera del sistema)*
- RF-16: Una entrada devuelta no muestra su QR al Cliente (CU-08 RF-9) ni cuenta
  para el límite de compra (CU-07 RF-21).

**Navegación**

- RF-17: EL SISTEMA ofrece «Devoluciones» en la navegación del Administrador.
  Ocultarlo a los demás roles es usabilidad: quien autoriza es el backend (RF-1).

## Casos límite

- **Compra con una entrada usada y dos activas:** se registran las dos activas;
  la usada no aparece.
- **Compra con una entrada ya devuelta y otra activa:** la compra aparece en
  pendientes, con la activa, y en devueltas, con la devuelta.
- **Entrada reactivada tras una postergación y el evento cancelado después:**
  está ACTIVA, así que entra en la devolución (decisiones.md → CU-13 devuelve
  solo entradas activas).
- **Evento cancelado sin ventas:** aparece en la lista con 0 pendientes, y al
  abrirlo se ve el aviso de FA-01.
- **Registrar dos veces** (doble clic, dos pestañas o dos Administradores): se
  registra una sola vez; el resto recibe el aviso de FA-02.
- **Id que no es un número en la URL:** no llega al backend.

## Fuera de alcance

- **La devolución económica y su comprobante:** ocurren fuera del sistema
  (`CLAUDE.md` → Cancelación).
- **Pagos tardíos con `requiere_devolucion`:** no tienen entradas, y ningún CU
  registra que se devolvieron (decisiones.md → Pago tardío).
- **La fecha y el responsable de la devolución:** el modelo no los tiene
  (decisión 1).
- **Deshacer una devolución:** la ficha no lo contempla.
- **Avisar al Cliente:** `CLAUDE.md` → Correos.
- **El reporte de ingresos (bruto, devuelto y neto):** CU-14.
