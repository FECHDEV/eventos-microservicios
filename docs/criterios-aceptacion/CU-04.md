# CU-04 — Gestionar datos personales — Criterios de aceptación

## Contexto

Cualquier Usuario con sesión iniciada (Cliente, Administrador o Personal
autorizado) consulta sus datos personales y actualiza los que puede modificar:
nombre, apellido, teléfono y contraseña. Cubre RF-04.

Fuentes: ficha CU-04 (`docs/casos-de-uso.md`); `docs/decisiones.md` →
Seguridad → "Datos personales (CU-04)", "Registro de clientes" (reglas de los
datos), "Inicio de sesión" (límite de intentos) y "Autenticación por JWT
stateless" (huella `hc`); tabla `usuario` (`docs/modelo-diseno-y-datos.md`
2.1); `CLAUDE.md` → Usuarios y roles.

RNF-01 (autenticación y autorización), RNF-02 (protección de credenciales) y
RNF-03 (protección de datos personales) se citan porque el caso muestra y
modifica datos personales y la contraseña.

## Requisitos funcionales (EARS)

**Consultar** *(ficha, pasos 1-2)*
- RF-1: SI la petición no tiene una sesión válida, ENTONCES EL SISTEMA rechaza la
  consulta, la actualización y el cambio de contraseña como no autenticados.
  *(precondición 1; CU-02)*
- RF-2: CUANDO el Usuario pide sus datos personales, EL SISTEMA muestra los de su
  cuenta: nombre, apellido, correo, teléfono, fecha de nacimiento (si es
  Cliente), rol, estado y fecha de registro, sin la contraseña ni su hash.
  *(paso 2; RNF-02)*
- RF-3: EL SISTEMA solo muestra y modifica la cuenta del Usuario de la sesión,
  nunca una indicada por un dato de la petición. *(RNF-03)*
- RF-4: EL SISTEMA aplica el mismo caso a los tres roles. *(ficha: actor
  abstracto Usuario)*

**Actualizar datos** *(ficha, pasos 3-5; postcondición 1)*
- RF-5: CUANDO el Usuario envía nombre, apellido y teléfono válidos, EL SISTEMA
  los registra y confirma la actualización devolviendo sus datos actualizados.
- RF-6: SI el nombre o el apellido faltan o superan 80 caracteres, o el teléfono
  supera 20, ENTONCES EL SISTEMA no registra cambios e indica los campos a
  corregir, con el mismo formato que CU-01. *(FA-01; decisiones.md → Registro
  de clientes)*
- RF-7: SI la actualización trae correo, fecha de nacimiento, rol, estado o
  contraseña, ENTONCES EL SISTEMA los ignora y no los modifica.
  *(decisiones.md → Datos personales)*
- RF-8: CUANDO el teléfono llega vacío, EL SISTEMA registra la cuenta sin
  teléfono. *(regla del registro)*
- RF-9: SI el Usuario no modifica ningún dato, ENTONCES EL SISTEMA termina sin
  alterar la cuenta. *(FA-02)*

**Cambiar la contraseña** *(decisiones.md → Datos personales; JWT stateless)*
- RF-10: CUANDO el Usuario envía su contraseña actual correcta y una nueva que
  cumple las reglas del registro, EL SISTEMA guarda la nueva (BCrypt) y responde
  con un token de sesión nuevo.
- RF-11: SI la contraseña actual no coincide o supera 72 bytes en UTF-8, ENTONCES
  EL SISTEMA no cambia la contraseña e informa que la contraseña actual es
  incorrecta.
- RF-12: SI falta la contraseña actual o la nueva, o la nueva no tiene al menos 8
  caracteres o supera 72 bytes en UTF-8, ENTONCES EL SISTEMA no cambia la
  contraseña e indica los campos a corregir.
- RF-13: CUANDO la contraseña cambia, EL SISTEMA deja de aceptar todos los tokens
  emitidos antes, incluido el de la sesión que hizo el cambio, desde la
  siguiente petición.
- RF-14: SI la contraseña actual no coincide, ENTONCES EL SISTEMA lo cuenta como
  intento fallido en el límite de inicio de sesión de ese correo desde esa IP.
- RF-15: MIENTRAS ese correo esté bloqueado desde esa IP, EL SISTEMA rechaza el
  cambio de contraseña (429 `INTENTOS_EXCEDIDOS`), aunque la contraseña actual
  sea correcta.
- RF-16: CUANDO la contraseña cambia, EL SISTEMA reinicia el conteo de intentos
  fallidos de ese correo desde esa IP.

## Casos límite

- **Teléfono vacío o solo con espacios:** la cuenta queda sin teléfono (RF-8).
- **Correo, fecha de nacimiento, rol o estado distintos en la petición:** se
  ignoran; la respuesta muestra los valores registrados (RF-7).
- **Contraseña nueva igual a la actual:** se acepta; no hay regla que lo impida.
- **Contraseña actual de más de 72 bytes:** es incorrecta aunque BCrypt la
  daría por buena, y cuenta como intento fallido (RF-11, RF-14).
- **Token anterior al cambio de contraseña:** responde 401; el token nuevo de la
  respuesta sí sirve (RF-10, RF-13).
- **Otra sesión del mismo Usuario en otro dispositivo:** deja de valer tras el
  cambio de contraseña (RF-13).
- **Cuenta desactivada:** no puede tener una sesión válida, así que no llega a
  este caso (RF-1; CU-02).
- **Rol cambiado por CU-09 después de iniciar sesión:** la consulta muestra el
  rol actual de la cuenta (RF-2; CU-02).

## Fuera de alcance

- Cambiar el correo o la fecha de nacimiento (`decisiones.md` → Datos
  personales).
- Cambiar el rol o el estado de una cuenta (CU-09).
- Consultar o modificar los datos de otro usuario (CU-09).
- Recuperar la contraseña sin sesión (CU-03).
- Eliminar la propia cuenta: no hay ficha que lo contemple.
- Pantalla de datos personales: frontend de Seguridad
  (`docs/plan-implementacion.md`).

## Criterios de finalización

- Cada RF con test en verde en `./mvnw test`: servicio, endpoints e integración
  de extremo a extremo. Los 153 tests de CU-01 a CU-03 siguen en verde.
- Prueba manual contra MySQL con `ana@mail.com`:
  - Sin token → 401; con token → sus datos, sin contraseña.
  - Actualizar nombre y teléfono → datos nuevos; correo y rol enviados en la
    petición se ignoran.
  - Datos inválidos → 400 con los campos a corregir.
  - Cambiar la contraseña con la actual incorrecta → error y no cambia.
  - Con la actual correcta → token nuevo; el token anterior da 401 y el nuevo
    funciona.
  - Cinco actuales incorrectas seguidas → la siguiente, 429.
  - Al terminar, ana vuelve a tener `secreta12` y sus datos originales.
- `/code-review` y `/security-review` sin hallazgos pendientes (CU-04 está en la
  lista de Seguridad de `CLAUDE.md`).
- Aquella entrega fue solo backend: la pantalla de datos personales se hizo
  después, al completar Seguridad en backend (`plan-implementacion.md`,
  excepción del subsistema de Seguridad). La pantalla, sus tests y su
  verificación están en
  `docs/superpowers/plans/2026-09-18-cu-04-frontend-datos-personales.md`.
