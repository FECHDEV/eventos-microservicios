# CU-09 — Gestionar usuarios — Criterios de aceptación

## Contexto

El Administrador consulta los usuarios registrados, les asigna uno de los tres
roles fijos (Cliente, Administrador, Personal autorizado) y activa o desactiva
sus cuentas. Cubre RF-06 y RF-07.

Fuentes: ficha CU-09 (`docs/casos-de-uso.md`); `docs/decisiones.md` → Seguridad
→ "Operaciones rechazadas en CU-09", "Gestión de usuarios (CU-09)", "Registro de
clientes" (fecha de nacimiento) y "Autenticación por JWT stateless"; tabla
`usuario` (`docs/modelo-diseno-y-datos.md` 2.1); `CLAUDE.md` → Usuarios y roles.

Se citan tres RNF:
- **RNF-01 (autenticación y autorización):** el caso es exclusivo del Administrador.
- **RNF-03 (protección de datos):** el listado muestra datos personales.
- **RNF-04 (integridad):** el sistema nunca queda sin administrador activo.

## Requisitos funcionales (EARS)

**Acceso** *(precondición 1)*
- RF-1: SI la petición no tiene una sesión válida, ENTONCES EL SISTEMA rechaza la
  consulta y los cambios como no autenticados (401 `NO_AUTENTICADO`). *(CU-02)*
- RF-2: SI el Usuario de la sesión no tiene rol ADMINISTRADOR, ENTONCES EL
  SISTEMA rechaza la consulta y los cambios (403 `ACCESO_DENEGADO`), con el mismo
  formato de error que el resto de la API. *(actor principal; `CLAUDE.md`: el
  control de acceso se valida en el backend)*

**Consultar** *(ficha, pasos 1-2)*
- RF-3: CUANDO el Administrador pide la lista de usuarios, EL SISTEMA muestra los
  usuarios registrados de todos los roles y estados, con nombre, apellido,
  correo, rol, estado y fecha de registro. No muestra la contraseña ni su hash,
  el teléfono o la fecha de nacimiento. *(paso 2; decisiones.md → Gestión de
  usuarios; RNF-03)*
- RF-4: EL SISTEMA muestra la lista por páginas de 20 usuarios, del registro más
  reciente al más antiguo, e informa el total de usuarios y de páginas. SI se
  pide un tamaño de página mayor a 100, ENTONCES EL SISTEMA usa 100.
  *(decisiones.md → Gestión de usuarios)*
- RF-5: CUANDO el Administrador filtra por rol, por estado o por un texto, EL
  SISTEMA muestra solo los usuarios que cumplen todos los filtros indicados. El
  texto se busca en el correo, el nombre y el apellido, sin distinguir
  mayúsculas. *(decisiones.md → Gestión de usuarios)*
- RF-6: SI un filtro de rol o de estado no es un valor válido, ENTONCES EL
  SISTEMA responde 400 `DATOS_INVALIDOS`.

**Cambiar el rol** *(ficha, pasos 3-6; postcondición 1)*
- RF-7: CUANDO el Administrador asigna a un usuario uno de los tres roles y la
  operación está permitida, EL SISTEMA registra el rol nuevo y confirma
  devolviendo el usuario actualizado.
- RF-8: SI el rol falta o no es CLIENTE, ADMINISTRADOR ni PERSONAL, ENTONCES EL
  SISTEMA no registra cambios y responde 400 `DATOS_INVALIDOS` indicando el
  campo. *(`CLAUDE.md`: tres roles fijos)*
- RF-9: CUANDO un usuario deja de ser CLIENTE, EL SISTEMA conserva su fecha de
  nacimiento. *(decisiones.md → Gestión de usuarios)*

**Cambiar el estado** *(FA-01; postcondición 1)*
- RF-10: CUANDO el Administrador desactiva la cuenta de un usuario y la operación
  está permitida, EL SISTEMA la registra como DESACTIVADA y confirma devolviendo
  el usuario actualizado. *(FA-01)*
- RF-11: CUANDO el Administrador reactiva una cuenta DESACTIVADA, EL SISTEMA la
  registra como ACTIVA sin otras validaciones. *(breve descripción de la ficha;
  decisiones.md → Gestión de usuarios)*
- RF-12: SI el estado falta o no es ACTIVA ni DESACTIVADA, ENTONCES EL SISTEMA no
  registra cambios y responde 400 `DATOS_INVALIDOS` indicando el campo.

**Operaciones no permitidas** *(FA-02; decisiones.md → Operaciones rechazadas en
CU-09 y Gestión de usuarios)*

En los cinco casos EL SISTEMA no registra cambios y responde 409 con un código
propio y un mensaje que indica el motivo.
- RF-13: SI el Administrador intenta cambiar su propio rol, ENTONCES EL SISTEMA lo
  rechaza (`ROL_PROPIO_NO_MODIFICABLE`). *(FA-02 a)*
- RF-14: SI el Administrador intenta desactivar su propia cuenta, ENTONCES EL
  SISTEMA lo rechaza (`CUENTA_PROPIA_NO_DESACTIVABLE`). *(FA-02 b)*
- RF-15: SI la operación le quitaría el rol ADMINISTRADOR al último administrador
  activo o lo desactivaría, ENTONCES EL SISTEMA la rechaza
  (`ULTIMO_ADMINISTRADOR_ACTIVO`). *(FA-02 c)*
- RF-16: SI se intenta cambiar el rol de una cuenta DESACTIVADA, ENTONCES EL
  SISTEMA lo rechaza (`ROL_DE_CUENTA_DESACTIVADA`). *(FA-02 d)*
- RF-17: SI se intenta asignar el rol CLIENTE a una cuenta sin fecha de
  nacimiento, ENTONCES EL SISTEMA lo rechaza (`FECHA_NACIMIENTO_REQUERIDA`).
  *(decisiones.md → Registro de clientes y Gestión de usuarios)*
- RF-18: SI el usuario indicado no existe, ENTONCES EL SISTEMA responde 404
  `USUARIO_NO_ENCONTRADO` sin registrar cambios.

**Simultaneidad y efecto de los cambios** *(postcondición 2; RNF-04)*
- RF-19: EL SISTEMA aplica RF-15 también a operaciones simultáneas. De dos
  operaciones que juntas dejarían al sistema sin administradores activos, solo
  una se registra y la otra responde 409 `ULTIMO_ADMINISTRADOR_ACTIVO`.
  *(decisiones.md → Gestión de usuarios)*
- RF-20: CUANDO cambia el rol de un usuario, EL SISTEMA le aplica los permisos del
  rol nuevo desde su siguiente petición, sin que tenga que volver a iniciar
  sesión. *(postcondición 2; decisiones.md → Autenticación por JWT stateless)*
- RF-21: CUANDO una cuenta queda desactivada, EL SISTEMA rechaza sus tokens desde
  la siguiente petición (401) y sus nuevos inicios de sesión con la contraseña
  correcta (403 `CUENTA_DESACTIVADA`). *(decisiones.md → Autenticación por JWT
  stateless; CU-02 FA-02)*
- RF-22: CUANDO una cuenta se reactiva, EL SISTEMA vuelve a aceptar su inicio de
  sesión con la contraseña que tenía. *(decisiones.md → Gestión de usuarios)*

## Casos límite

- **Mismo rol o mismo estado que el actual:** responde 200 sin alterar la
  cuenta. Las reglas RF-13 a RF-17 se evalúan antes de comparar con el valor
  actual: por ejemplo, asignarse el propio rol, aunque sea el mismo, se rechaza.
- **Desactivar una cuenta ya desactivada:** responde 200 sin cambios.
- **Promover a ADMINISTRADOR:** se permite desde CLIENTE o PERSONAL si la cuenta
  está activa. No hace falta ninguna regla extra: no afecta al conteo de RF-15.
- **Varios motivos a la vez:** si una operación cae en más de una regla, responde
  el código de la primera en el orden RF-13 a RF-17.
- **RF-15 sin operaciones simultáneas:** no se alcanza por la API, porque quien
  opera es un administrador activo distinto del afectado. Se prueba en el
  servicio y con dos operaciones simultáneas (RF-19).
- **Administrador inicial:**
  - No tiene fecha de nacimiento, así que no puede pasar a CLIENTE (RF-17).
  - Sí puede pasar a PERSONAL o desactivarse si queda otro administrador activo
    que haga la operación.
- **Un CLIENTE promovido y luego devuelto a CLIENTE:** conserva la fecha, así que
  se permite (RF-9, RF-17).
- **Filtros sin resultados o página fuera de rango:** lista vacía con los totales
  correctos, no un error.
- **Texto de búsqueda vacío o solo con espacios:** no filtra.
- **Usuario afectado con una petición en curso:** esa petición termina con los
  permisos con los que empezó; el cambio rige desde la siguiente (RF-20, RF-21).
- **Cuenta desactivada con un token de recuperación vigente:** sigue pudiendo
  restablecer la contraseña sin reactivarse (CU-03).

## Fuera de alcance

- Crear o eliminar usuarios. El registro es CU-01 y el Administrador inicial lo
  crea la carga inicial de datos (`CLAUDE.md`).
- Modificar los datos personales o la contraseña de otro usuario (CU-04 es solo
  sobre la propia cuenta; CU-03).
- Roles nuevos o permisos individuales: no es RBAC (`CLAUDE.md`).
- Notificar al usuario el cambio de rol o de estado. Los correos del sistema son
  tres y ninguno lo cubre (`CLAUDE.md` → Correos).
- Historial de cambios de rol o de estado: no está en el modelo.
- Cortar una petición que ya está en curso cuando cambia el rol o el estado.
- Pantalla de gestión de usuarios: frontend de Seguridad
  (`docs/plan-implementacion.md`).

## Criterios de finalización

- Cada RF con test en verde en `./mvnw test`: entidad, repositorio, servicio,
  endpoints e integración de extremo a extremo, con dos operaciones simultáneas
  para RF-19. Los 179 tests de CU-01 a CU-04 siguen en verde.
- Prueba manual contra MySQL, con el Administrador inicial y `ana@mail.com`:
  - **Acceso:** sin token → 401; con el token de ana (CLIENTE) → 403 con el
    formato de la API.
  - **Listado:** el Administrador ve la primera página, filtra por rol CLIENTE y
    busca "ana".
  - **Pasar a ana a PERSONAL:** con su mismo token, la consulta de sus datos
    muestra el rol nuevo y la lista de usuarios le sigue dando 403.
  - **Pasar a ana a ADMINISTRADOR:** con su mismo token puede ver la lista. Desde
    la cuenta de ana, pasar al Administrador inicial a CLIENTE → 409
    `FECHA_NACIMIENTO_REQUERIDA`.
  - **Desactivar a ana:**
    - Su token da 401 y su inicio de sesión da 403.
    - Cambiarle el rol → 409 `ROL_DE_CUENTA_DESACTIVADA`.
    - Al reactivarla vuelve a iniciar sesión.
  - **Sobre la propia cuenta:** el Administrador cambia su propio rol → 409, y se
    desactiva → 409.
  - **Usuario inexistente:** → 404.
  - **Al terminar:** ana vuelve a CLIENTE y ACTIVA.
- `/code-review` y `/security-review` sin hallazgos pendientes (CU-09 está en la
  lista de Seguridad de `CLAUDE.md`).
- Aquella entrega fue solo backend: la pantalla de gestión de usuarios se hizo
  después, al completar Seguridad en backend (`plan-implementacion.md`,
  excepción del subsistema de Seguridad). La pantalla, sus tests y su
  verificación están en
  `docs/superpowers/plans/2026-09-18-cu-09-frontend-gestion-usuarios.md`.
