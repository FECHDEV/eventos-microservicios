# Criterios de aceptación — CU-02

## Contexto

Cualquier Usuario (Cliente, Administrador o Personal autorizado) se autentica
con su correo y su contraseña para acceder a las funcionalidades que
corresponden a su rol. Cubre RF-02 (Inicio de sesión).

Fuentes: ficha CU-02 en `casos-de-uso.md`; "1. Seguridad" en `decisiones.md`
(Autenticación por JWT stateless, Contraseñas con BCrypt, Registro de clientes,
Inicio de sesión, Administrador inicial con `CommandLineRunner`); tabla
`usuario` en `modelo-diseno-y-datos.md`; "Usuarios y roles" en `CLAUDE.md`;
RNF-01 y RNF-02, que `CLAUDE.md` asocia a la revisión de este CU.

Ampliado el 30/10/2026: RF-7 a RF-9 y RF-21 se resuelven entre el gateway y
Seguridad (`decisiones.md` → «Sesión»), y RF-18 exige la complejidad de CU-01 RF-16.

## Requisitos funcionales (EARS)

**Flujo principal**

- RF-1: CUANDO el Usuario envía el correo y la contraseña de una cuenta ACTIVA,
  EL SISTEMA lo autentica y le entrega un token de acceso, su vencimiento y sus
  datos con el rol. *(Flujo principal, pasos 3-5; postcondición 1)*
- RF-2: EL SISTEMA acepta la solicitud de inicio de sesión sin sesión iniciada.
  *(Paso 1)*
- RF-3: EL SISTEMA busca la cuenta con el correo en minúsculas y sin espacios
  alrededor, igual que al registrarse. *(`decisiones.md`: Registro de clientes,
  Inicio de sesión)*
- RF-4: CUANDO el sistema entrega un token, EL SISTEMA lo firma y lo hace vencer
  8 horas después de emitirlo, sin refresh token. *(`decisiones.md`:
  Autenticación por JWT stateless; `CLAUDE.md`)*
- RF-5: EL SISTEMA no incluye la contraseña ni su hash en la respuesta ni en el
  token. El token solo lleva una huella derivada del hash, que no permite
  reconstruirlo. *(`decisiones.md`: Contraseñas con BCrypt, Autenticación por
  JWT stateless; RNF-02)*
- RF-6: EL SISTEMA aplica el mismo inicio de sesión a los roles CLIENTE,
  ADMINISTRADOR y PERSONAL. *(Ficha: actor abstracto Usuario, heredado por los
  tres)*

**Acceso posterior con el token**

- RF-7: CUANDO una petición a una funcionalidad protegida trae en el header
  `Authorization` un token válido y vigente, EL SISTEMA la atiende como el
  Usuario del token, con el rol que tiene la cuenta en ese momento. *(Paso 5;
  `decisiones.md`: Autenticación por JWT stateless)*
- RF-8: SI una petición a una funcionalidad protegida no trae token, o lo trae
  vencido, alterado o mal formado, ENTONCES EL SISTEMA la rechaza como no
  autenticada. *(RNF-01; `CLAUDE.md`: el control de acceso se valida en el
  backend)*
- RF-9: MIENTRAS la cuenta del token esté DESACTIVADA o ya no exista, EL SISTEMA
  rechaza sus peticiones como no autenticadas, aunque el token no haya vencido.
  *(FA-02; `decisiones.md`: Autenticación por JWT stateless)*
- RF-10: SI un Usuario autenticado pide una funcionalidad que su rol no permite,
  ENTONCES EL SISTEMA la rechaza como acceso denegado. *(Paso 5; RNF-01)*

**FA-01 — Credenciales incorrectas**

- RF-11: SI el correo no corresponde a ninguna cuenta o la contraseña no
  coincide, ENTONCES EL SISTEMA informa que las credenciales son incorrectas,
  con el mismo mensaje en ambos casos, y no entrega token. *(FA-01, pasos
  4.1-4.3; `decisiones.md`: Inicio de sesión)*
- RF-12: SI falta el correo o la contraseña, ENTONCES EL SISTEMA no intenta
  autenticar e indica los campos a corregir, con el mismo formato de errores que
  CU-01. *(Paso 3)*
- RF-13: SI la contraseña supera 72 bytes en UTF-8, ENTONCES EL SISTEMA responde
  que las credenciales son incorrectas, aunque BCrypt la daría por buena al
  compararla. *(`decisiones.md`: Registro de clientes, Inicio de sesión)*

**FA-02 — Cuenta desactivada**

- RF-14: SI la cuenta está DESACTIVADA y la contraseña es correcta, ENTONCES EL
  SISTEMA informa que la cuenta no puede acceder al sistema y no entrega token.
  *(FA-02, pasos 4.1-4.3)*
- RF-15: SI la cuenta está DESACTIVADA y la contraseña es incorrecta, ENTONCES
  EL SISTEMA responde como en RF-11. *(`decisiones.md`: Inicio de sesión)*

**Configuración y Administrador inicial**

- RF-16: CUANDO la aplicación arranca y no existe ningún usuario con rol
  ADMINISTRADOR, EL SISTEMA crea uno en estado ACTIVA con el correo de
  `EVENTOS_ADMIN_CORREO` (normalizado), la contraseña de
  `EVENTOS_ADMIN_PASSWORD` hasheada con BCrypt, nombre "Administrador" y
  apellido "Inicial". *(`CLAUDE.md`: el Administrador inicial se crea en el
  despliegue; `decisiones.md`: Administrador inicial con `CommandLineRunner`)*
- RF-17: CUANDO la aplicación arranca y ya existe al menos un ADMINISTRADOR, EL
  SISTEMA no crea otro ni modifica los existentes. *(`decisiones.md`:
  idempotente)*
- RF-18: SI no existe ningún ADMINISTRADOR y falta alguna de las dos variables,
  o no cumplen las reglas de correo y contraseña del registro (CU-01), ENTONCES
  la aplicación no arranca e indica qué hay que configurar. *(`decisiones.md`:
  Administrador inicial con `CommandLineRunner`)*
- RF-19: SI no existe ningún ADMINISTRADOR y el correo configurado ya pertenece
  a otra cuenta, ENTONCES la aplicación no arranca y no le cambia el rol a esa
  cuenta. *(`CLAUDE.md`: los roles los asigna un Administrador en CU-09)*
- RF-20: SI `EVENTOS_JWT_SECRETO` falta, no es base64 o tiene menos de 256 bits,
  ENTONCES la aplicación no arranca e indica la variable. *(`decisiones.md`:
  Autenticación por JWT stateless)*

**Protección del acceso** *(agregado tras la revisión de seguridad;
`decisiones.md`: Autenticación por JWT stateless, Inicio de sesión)*

- RF-21: SI la contraseña de la cuenta cambió después de emitir el token,
  ENTONCES EL SISTEMA rechaza sus peticiones como no autenticadas, aunque el
  token no haya vencido.
- RF-22: SI se registran 5 intentos fallidos de inicio de sesión para el mismo
  correo desde la misma dirección IP dentro de 15 minutos, ENTONCES EL SISTEMA
  rechaza durante 15 minutos los intentos de ese correo desde esa dirección,
  aunque las credenciales sean correctas, e informa que hay que esperar.
- RF-23: CUANDO un inicio de sesión es exitoso, EL SISTEMA reinicia el conteo de
  intentos fallidos de ese correo desde esa dirección.

## Casos límite

- `Ana@Mail.COM ` inicia sesión en la cuenta `ana@mail.com`.
- La contraseña sí distingue mayúsculas: `Secreta12` no entra a una cuenta con
  `secreta12`.
- **Contraseña registrada de exactamente 72 bytes:** la misma con caracteres de
  más → credenciales incorrectas (RF-13), aunque BCrypt la truncaría y
  coincidiría.
- **Correo inexistente:** también ejecuta una comparación BCrypt, para que la
  demora de la respuesta no revele qué correos tienen cuenta (RF-11).
- **Registro o inicio de sesión con un token inválido o vencido en el header** →
  el token se ignora y la petición se atiende sin sesión.
- **No autenticado (RF-8):**
  - Header `Authorization` sin el prefijo `Bearer `.
  - Token firmado con otra clave.
  - Payload alterado.
  - Token vencido, sin tolerancia de reloj.
  - Token sin huella de la contraseña.
- **Cuenta desactivada después de emitir el token** → su siguiente petición se
  rechaza (RF-9).
- **Rol cambiado después de emitir el token** → la siguiente petición usa el rol
  nuevo (RF-7).
- **Contraseña cambiada después de emitir el token** → su siguiente petición se
  rechaza (RF-21). Cambiar la contraseña llega con CU-03 y CU-04; hasta
  entonces se prueba modificando el hash directamente.
- **Varias sesiones del mismo usuario** en distintos dispositivos → todas
  válidas; cada inicio de sesión emite un token independiente.
- **Intentos fallidos (RF-22):**
  - Los correos inexistentes también suman intentos, para no revelar cuáles
    existen.
  - El mismo correo desde otra IP, u otro correo desde la misma IP, no queda
    bloqueado.
  - Una cuenta desactivada con la contraseña correcta no suma: no son
    credenciales incorrectas.
  - Los datos que faltan también responden como en RF-12 y no suman intento.
  - Los contadores viven en memoria: se pierden al reiniciar la aplicación y
    valen para una sola instancia del backend.
- **Arranque con un administrador existente y sin las variables del admin** →
  arranca normalmente (RF-17).
- **Único administrador desactivado** → no se crea otro, porque la regla mira el
  rol y no el estado. CU-09 impide llegar a esa situación (último administrador
  activo, `decisiones.md`).

## Fuera de alcance

- Refresh token o renovación del token (`CLAUDE.md`: JWT sin refresh token).
- Cerrar sesión en el servidor o llevar una lista de tokens revocados: no hay
  ficha de cierre de sesión, y con JWT stateless cerrar sesión es descartar el
  token en el frontend.
- Bloqueo permanente de la cuenta o desbloqueo por un administrador: el límite de
  RF-22 es temporal y por correo e IP.
- Configurar el reenvío de la IP real detrás de un proxy inverso: se hace al
  desplegar (`decisiones.md`: Inicio de sesión).
- Qué funcionalidades corresponden a cada rol: lo define cada CU. CU-02 deja
  funcionando la autenticación y los rechazos por falta de sesión o de permiso.
- Recuperar la contraseña (CU-03), cambiar los datos personales (CU-04), asignar
  roles o desactivar cuentas (CU-09).

## Criterios de finalización

- Cada RF con al menos un test en verde en `./mvnw test`: servicio, endpoint,
  filtro del token y arranque del Administrador inicial. Los tests de CU-01
  siguen en verde.
- **Prueba manual contra MySQL:**
  - Inicio de sesión de `ana@mail.com`, también con otras mayúsculas y
    espacios → token.
  - Contraseña incorrecta → credenciales incorrectas.
  - Inicio de sesión del Administrador inicial creado desde las variables.
  - Petición protegida sin token → no autenticada.
  - Con token → pasa el control de sesión.
  - Cuenta desactivada a mano en la base → FA-02 al iniciar sesión, y su token
    anterior se rechaza.
  - Hash de la contraseña reemplazado a mano en la base → el token anterior se
    rechaza.
  - 5 intentos fallidos → el sexto se rechaza por exceso de intentos.
- **Arranque:**
  - Sin `EVENTOS_JWT_SECRETO` → la aplicación no arranca.
  - Sin administrador y sin sus variables → tampoco arranca.
- `/code-review` y `/security-review` sin hallazgos pendientes (`CLAUDE.md`,
  revisión antes del PR).
- La pantalla de inicio de sesión entra con HU-09.
