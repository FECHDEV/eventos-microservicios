# Criterios de aceptación — CU-01

## Contexto

El Cliente crea su propia cuenta con sus datos personales, incluida su fecha de
nacimiento, para poder iniciar sesión después y adquirir entradas. Cubre RF-01
(Registro de usuarios) y RF-05 (Registro de fecha de nacimiento).

Fuentes: ficha CU-01 en `casos-de-uso.md`; "1. Seguridad" en `decisiones.md`
(Registro de clientes, Contraseñas con BCrypt); clase `Usuario`/`Cliente` y
tabla `usuario` en `modelo-diseno-y-datos.md`; "Usuarios y roles" en
`CLAUDE.md`.

Ampliado el 30/10/2026 con la complejidad de la contraseña
(`decisiones.md` → «Complejidad de la contraseña»).

## Requisitos funcionales (EARS)

**Flujo principal**

- RF-1: CUANDO el Cliente envía sus datos completos y válidos con un correo que
  no pertenece a ninguna cuenta, EL SISTEMA registra la cuenta y confirma que el
  registro se realizó correctamente. *(Flujo principal, pasos 3-6)*
- RF-2: CUANDO el sistema registra una cuenta, EL SISTEMA le asigna el rol
  CLIENTE, sin importar lo que indique la solicitud. *(`CLAUDE.md`: todo usuario
  que se registra por sí mismo obtiene rol Cliente)*
- RF-3: CUANDO el sistema registra una cuenta, EL SISTEMA la deja en estado
  ACTIVA, sin confirmación por correo. *(Postcondición 3; `decisiones.md`)*
- RF-4: CUANDO el sistema registra una cuenta, EL SISTEMA almacena la fecha de
  nacimiento y la fecha y hora del registro. *(Postcondición 2; `fecha_registro`
  NOT NULL)*
- RF-5: CUANDO el sistema registra una cuenta, EL SISTEMA guarda el correo en
  minúsculas y sin espacios alrededor. *(`decisiones.md`)*
- RF-6: EL SISTEMA almacena la contraseña como hash BCrypt, nunca en texto
  plano, y no la incluye en ninguna respuesta. *(`decisiones.md`: Contraseñas
  con BCrypt)*
- RF-7: EL SISTEMA acepta la solicitud de registro sin sesión iniciada.
  *(Precondición 1: quien se registra todavía no tiene cuenta)*
- RF-8: EL SISTEMA permite registrar la cuenta sin teléfono. *(`telefono` sin
  NOT NULL)*

**FA-01 — Datos incompletos o inválidos**

- RF-9: SI uno o más datos están incompletos o no cumplen su formato, ENTONCES
  EL SISTEMA no registra la cuenta e indica todos los campos a corregir.
  *(FA-01, pasos 4.1-4.3)*
- RF-10: SI falta el nombre, el apellido, el correo, la contraseña o la fecha
  de nacimiento, ENTONCES EL SISTEMA lo trata como dato incompleto (RF-9).
  *(NOT NULL en `usuario`; `fecha_nacimiento` obligatoria para CLIENTE en
  `decisiones.md`)*
- RF-11: SI el correo no tiene formato de dirección de correo, ENTONCES EL
  SISTEMA lo trata como dato inválido (RF-9). *(FA-01)*
- RF-12: SI la contraseña tiene menos de 8 caracteres o más de 72 bytes en
  UTF-8, ENTONCES EL SISTEMA la trata como dato inválido (RF-9).
  *(`decisiones.md`)*
- RF-13: SI la fecha de nacimiento es posterior al día en curso, ENTONCES EL
  SISTEMA la trata como dato inválido (RF-9). *(`decisiones.md`)*
- RF-14: SI el nombre o el apellido superan 80 caracteres, el correo 120 o el
  teléfono 20, ENTONCES EL SISTEMA los trata como datos inválidos (RF-9).
  *(Longitudes de la tabla `usuario`)*

- RF-16: SI la contraseña no tiene al menos una mayúscula, una minúscula y un
  número, ENTONCES EL SISTEMA la trata como dato inválido (RF-9).
  *(`decisiones.md`: Complejidad de la contraseña)*

**FA-02 — Cuenta ya existente**

- RF-15: SI ya existe una cuenta con el mismo correo, comparado sin distinguir
  mayúsculas ni espacios alrededor, ENTONCES EL SISTEMA informa que la cuenta ya
  existe y finaliza sin registrarla. *(FA-02; `correo` UNIQUE;
  `decisiones.md`)*

## Casos límite

- **Registro simultáneo con el mismo correo:** la restricción UNIQUE de
  `correo` resuelve la carrera; la solicitud que pierde termina como FA-02
  (RF-15), no como error interno.
- **Correo de una cuenta desactivada:** sigue siendo una cuenta existente →
  FA-02. La unicidad de `correo` no depende del estado.
- `Juan@Mail.com ` contra una cuenta `juan@mail.com` → FA-02.
- **Campos con solo espacios** (`"   "`) en nombre, apellido o correo → dato
  incompleto.
- **Contraseña en el borde:** 7 caracteres se rechaza, 8 se acepta; 72 bytes se
  acepta, 73 se rechaza. Los caracteres multibyte (ñ, tildes, emoji) cuentan por
  bytes para el máximo.
- **Fecha de nacimiento igual a hoy** → se acepta; solo se rechaza la futura.
- **Solicitud que envía `rol` o `estado`** (por ejemplo ADMINISTRADOR o
  DESACTIVADA) → se ignoran; la cuenta queda CLIENTE y ACTIVA.
- **Teléfono ausente o vacío** → se registra sin teléfono. Solo se valida su
  longitud máxima.
- **Varios campos inválidos a la vez** → la respuesta los indica todos, no solo
  el primero.

## Fuera de alcance

- Confirmación de la cuenta por correo (`decisiones.md`: activa sin
  confirmación).
- Iniciar sesión o emitir un token al registrarse: es CU-02 (la ficha dice
  "posteriormente iniciar sesión").
- Crear Administradores o Personal autorizado: los asigna un Administrador en
  CU-09, y el Administrador inicial lo crea la carga inicial de datos
  (`CLAUDE.md`).
- Edad mínima para registrarse: la edad se valida por evento al comprar (CU-06).

## Criterios de finalización

- Cada RF con al menos un test en verde en `./mvnw test`: servicio (unitario) y
  endpoint.
- Prueba manual del endpoint de registro: alta exitosa, correo duplicado
  (también con otras mayúsculas) y campo faltante.
- En la base: contraseña guardada como hash BCrypt, correo en minúsculas, rol
  CLIENTE, estado ACTIVA y `fecha_registro` completa.
- `/code-review` y `/security-review` sin hallazgos pendientes (`CLAUDE.md`,
  revisión antes del PR).
- El formulario de registro entra con HU-09, con la misma regla de contraseña.
