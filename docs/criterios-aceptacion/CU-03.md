# CU-03 — Recuperar contraseña — Criterios de aceptación

## Contexto

Cualquier Usuario (Cliente, Administrador o Personal autorizado) que no
puede acceder a su cuenta la recupera con su correo registrado, sin
necesidad de tener sesión iniciada. Interviene el actor secundario
"Servicio de correo electrónico" a través de una interfaz propia
`NotificadorCorreo`. Cubre RF-03.

Fuentes: ficha CU-03 (`docs/casos-de-uso.md`); `docs/decisiones.md` →
Seguridad → "Recuperación de contraseña" y "Recuperación de contraseña en
tabla aparte"; `docs/decisiones.md` → Notificaciones; tabla
`recuperacion_contrasena` (`docs/modelo-diseno-y-datos.md` 2.9).

RNF-01 (autenticación/autorización) y RNF-02 (protección de credenciales)
se citan igual que en CU-02, porque esta operación cambia la contraseña de
una cuenta sin sesión iniciada.

---

## Solicitar recuperación *(ficha, pasos 1-5)*

- RF-1: EL SISTEMA acepta la solicitud de recuperación sin sesión
  iniciada.
- RF-2: EL SISTEMA busca la cuenta con el correo normalizado (minúsculas,
  sin espacios alrededor), igual que en registro e inicio de sesión.
- RF-3: EL SISTEMA responde siempre el mismo mensaje de confirmación,
  exista o no una cuenta con ese correo, sin indicar cuál es el caso.
  *(FA-01 reinterpretado: decisión del usuario para no revelar cuentas,
  mismo criterio que CU-02)*
- RF-4: CUANDO el correo corresponde a una cuenta, EL SISTEMA genera un
  token aleatorio de al menos 256 bits, guarda su hash SHA-256 (nunca el
  token original) con `fecha_creacion` en ese momento, `fecha_expiracion`
  una hora después y `usado = false`, e invalida (`usado = true`) cualquier
  token vigente anterior de esa misma cuenta. *(`decisiones.md` →
  Recuperación de contraseña; RNF-02)*
- RF-5: CUANDO genera el token, EL SISTEMA solicita a `NotificadorCorreo`
  el envío del mensaje de recuperación con ese token. *(paso 5 de la
  ficha)*
- RF-6: EL SISTEMA aplica el mismo flujo a los tres roles. *(ficha: actor
  abstracto Usuario)*
- RF-7: EL SISTEMA permite solicitar la recuperación de una cuenta
  DESACTIVADA, sin reactivarla ni revelar su estado.

## Límite de solicitudes

- RF-8: SI se superan 3 solicitudes para el mismo correo desde la misma IP
  en 15 minutos, ENTONCES EL SISTEMA rechaza nuevas solicitudes de ese
  correo desde esa IP durante 15 minutos (429 `SOLICITUDES_EXCEDIDAS`).
- RF-9: Los correos inexistentes también cuentan para este límite, para no
  revelar cuáles existen por esta vía.

## Restablecer contraseña *(ficha, pasos 6-7; postcondiciones 1-2)*

- RF-10: CUANDO el Usuario envía un token vigente y no usado junto con una
  nueva contraseña válida, EL SISTEMA actualiza la contraseña (BCrypt),
  marca ese token `usado = true` e invalida cualquier otro token vigente
  de la misma cuenta.
- RF-11: SI falta el token o la nueva contraseña, o la contraseña no
  cumple las reglas del registro (8 caracteres o más, mayúscula, minúscula y
  número, máximo 72 bytes UTF-8), ENTONCES EL SISTEMA no la acepta e indica los campos a corregir,
  con el mismo formato que CU-01/CU-02.
- RF-12: SI el hash SHA-256 del token recibido no corresponde a ningún
  registro, o el registro está vencido o ya fue usado, ENTONCES EL SISTEMA
  responde que el proceso de recuperación no es válido o venció, con el
  mismo mensaje en los tres casos, y no cambia la contraseña. *(FA-02)*
- RF-13: EL SISTEMA permite restablecer la contraseña de una cuenta
  DESACTIVADA, sin reactivarla ni revelar su estado.
- RF-14: DESPUÉS de restablecer la contraseña, EL SISTEMA deja de aceptar
  los tokens de sesión (JWT) emitidos antes del cambio, desde la siguiente
  petición. *(cubierto por la huella `hc` de CU-02; se verifica, no se
  reimplementa)*
- RF-15: CUANDO se restablece la contraseña, EL SISTEMA quita el bloqueo por
  intentos fallidos de inicio de sesión de esa cuenta desde todas las IPs, para
  que pueda entrar enseguida con la contraseña nueva. *(`decisiones.md` →
  Inicio de sesión; surgió de `/code-review`)*

## Casos límite

- **Correo:** ` Ana@Mail.COM ` encuentra la cuenta `ana@mail.com`.
- **Solicitudes seguidas:** dos solicitudes válidas seguidas para el mismo
  correo → solo el token de la segunda sirve; el de la primera responde
  FA-02 si se intenta usar.
- **Token de otra cuenta:** un token vigente solo cambia la contraseña de
  la cuenta a la que pertenece.
- **Reutilizar un token ya usado:** la segunda vez responde FA-02 (RF-12).
- **Usar el valor guardado en la base como token:** responde FA-02, porque
  se hashea de nuevo y no coincide con ningún registro (RF-4, RF-12).
- **Nueva contraseña igual a la anterior:** se acepta; no hay regla que lo
  impida.
- **Cuenta desactivada:** puede solicitar y completar la recuperación
  (RF-7, RF-13); seguir DESACTIVADA no cambia con esto (eso corresponde a
  CU-09).

## Fuera de alcance

- Envío real de correo: usa el simulador (`NotificadorCorreo`); el
  adaptador SMTP se conecta cerca del despliegue, sin cambios en este CU.
- CAPTCHA u otra protección antibots en la solicitud.
- Notificar al dueño de la cuenta que alguien intentó recuperarla.
- Pantallas de recuperación: frontend de Seguridad
  (`docs/plan-implementacion.md`).
- CU-01, CU-02, CU-04 y CU-09.

## Criterios de finalización

- Cada RF con test en verde en `./mvnw test`: servicio, endpoint,
  repositorio, límite de solicitudes y verificación del `hc` tras el
  cambio de contraseña. Los 106 tests de CU-01/CU-02 siguen en verde.
- Prueba manual contra MySQL, usando el simulador (log del backend en vez
  del buzón real):
  - Solicitar con `ana@mail.com` → mismo mensaje que con un correo
    inexistente; el log muestra el token.
  - La fila de `recuperacion_contrasena` guarda un hash de 64 caracteres
    hexadecimales distinto del token del log; usar ese hash como token →
    FA-02.
  - Restablecer con ese token → 200; iniciar sesión con la contraseña
    nueva funciona y con la vieja no.
  - Reutilizar el mismo token → FA-02.
  - Pedir dos veces seguidas y usar el token de la primera → FA-02.
  - Token vencido (forzando la fecha en la base) → FA-02.
  - 4 solicitudes seguidas del mismo correo → la cuarta, 429.
  - Un JWT emitido antes del restablecimiento → 401 después (RF-14).
- `/code-review` y `/security-review` sin hallazgos pendientes (CU-03 está
  en la lista de Seguridad de `CLAUDE.md`).
- Aquella entrega fue solo backend: las pantallas de recuperación se hicieron
  después, al completar Seguridad en backend (`plan-implementacion.md`,
  excepción del subsistema de Seguridad). Las pantallas, sus tests y su
  verificación están en
  `docs/superpowers/plans/2026-09-17-cu-03-frontend-recuperacion.md`.
